# Сервисы OpenSSL core

SDK сохраняет входящий `OSSL_DISPATCH` как типизированные указатели в отдельном
приватном контексте каждого экземпляра провайдера. Глобальной
таблицы нет. OpenSSL передаёт этот контекст в callbacks алгоритмов как `provctx`.
Полученные функции не заменяются после инициализации.

## Обёртки

- `ops_crt.h`: все 12 входящих функций памяти, включая secure allocation,
  realloc, очистку и освобождение. `ops_memset` и `ops_memcpy` удалены:
  соответствующих core callbacks нет.
- `ops_bio.h`: все 11 входящих BIO-функций; используются родные `OSSL_CORE_BIO *`.
- `ops_core.h`: параметры, ошибки, thread callbacks, OBJ, entropy/nonce,
  self-test/indicator callbacks и доступ к провайдерам.

Обёрнуты все 53 входящие core-функции из заголовков OpenSSL 3.5.
Новые относительно OpenSSL 3.0 объявления защищены проверками соответствующих
`OSSL_FUNC_*`. Сигнатуры и native-типы сохранены с добавлением первого аргумента
`void *provctx`. Функции памяти скрывают служебные `file`/`line`;
эти значения указывают на реализацию обёртки.

Для собственных core-параметров, ошибок, entropy/nonce и регистрации child
callbacks handle берётся из `ctx`. Для обращения к другому провайдеру handle
остаётся явным аргументом. `OPENSSL_CORE_CTX *` в self-test/indicator callbacks
сохраняет свой родной тип: его нельзя трактовать как `OSSL_LIB_CTX *`.

Пользовательская структура хранится отдельно: пользователь определяет
`ops_provider_user_init` и `ops_provider_user_cleanup`, доступ выполняется через
`ops_provider_get_user_data(provctx)` из `ops_provider.h`.
См. [контракт lifecycle](provider-lifecycle.md).

Публичного типа контекста нет: его представление известно только SDK.
Пользователь не создаёт структуру и не выполняет приведение типов.
Нельзя передавать произвольный указатель или контекст другого провайдера.

## Использование и время жизни

```c
#include "openssl_provider_sdk/ops_crt.h"
#include "openssl_provider_sdk/ops_core.h"

/* Внутри callback алгоритма: provctx — аргумент, полученный от OpenSSL. */
void *buffer = ops_malloc(provctx, 128);
if (buffer != NULL)
{
    if (ops_core_has_function(provctx, OSSL_FUNC_OPENSSL_CLEANSE))
    {
        ops_cleanse(provctx, buffer, 128);
    }
    ops_free(provctx, buffer);
}
```

Алгоритм сохраняет заимствованный `void *provctx`, полученный от OpenSSL,
в своём контексте,
чтобы передать его при последующих вызовах, включая освобождение.
Контекст SDK должен оставаться живым до освобождения связанных ресурсов.
Память и BIO разных экземпляров или семейств allocator смешивать нельзя.
Secure allocations освобождаются соответствующими secure-функциями.
Результаты, владение и требования к буферам следуют родному контракту OpenSSL.

При init обязательны `CRYPTO_malloc` и `CRYPTO_free`: SDK использует их даже
для собственного контекста. Отсутствие функции или отказ выделения приводит
к отказу init с `out = NULL` и `provctx = NULL`. Системного allocator fallback нет.
Teardown освобождает контекст через allocator того же экземпляра.

Остальные callbacks необязательны. Перед вызовом проверьте их наличие через
`ops_core_has_function(ctx, OSSL_FUNC_...)`. Вызов отсутствующей функции,
вызов с недействительным контекстом или после teardown нарушает контракт.
SDK не подменяет недоступные сервисы локальными реализациями.

## Проверки

`core_dispatch` создаёт два экземпляра с разными allocator/BIO/core callbacks,
проверяет независимость, освобождение через исходный allocator, отсутствие
необязательной функции и отказ init. `core_live` загружает два настоящих экземпляра, проверяет native memory/BIO
и использование второго после teardown первого. Тестовые алгоритмы используют `ops_malloc`
и `ops_free`; их загрузка и вычисление digest проверяются настоящим OpenSSL CLI.
