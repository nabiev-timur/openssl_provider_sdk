# Политика объявления и доставки алгоритмов

## Статус и назначение

Документ фиксирует согласованный контракт развития SDK. Часть решений ещё
не реализована. Инструкция по существующему digest-интерфейсу находится в
[руководстве регистрации](digest-registration.md).

SDK предоставляет удобный способ доставить таблицы функций пользователя
в OpenSSL. Пользователь реализует callbacks алгоритма и объявляет его;
стандартную инициализацию провайдера, публикацию таблиц и завершение работы
организует SDK. Более сложный источник таблиц подключается отдельно, без
обязательной переписи всего провайдера.

## Граница ответственности

| SDK | Пользователь |
|---|---|
| Собирает объявления и доставляет таблицы OpenSSL | Реализует функции алгоритмов |
| Скрывает платформенные правила секций и компоновки | Выбирает идентификаторы callbacks, имена и свойства |
| В автоматическом режиме добавляет терминаторы списков и dispatch | Отвечает за смысл и корректность переданных записей |
| Организует стандартный жизненный цикл провайдера | Через согласованные точки расширения готовит собственное состояние |

SDK не проверяет полноту callbacks, соответствие ID сигнатуре, корректность
свойств или криптографическую реализацию. Он не удаляет дубликаты, не разрешает
конфликты имён и не фильтрует объявления. Повторное объявление одного алгоритма
сохраняется отдельной записью. Одинаковые имена с разными свойствами также
доставляются без преобразования.

Это относится к содержимому алгоритмов. Корректное размещение секций,
терминаторы и сохранение записей при компоновке остаются обязанностью SDK.
Уникальность C-символов и разрешение имён алгоритмов OpenSSL — разные вопросы.

## Общий механизм для операций

Используются родные структуры OpenSSL: `OSSL_ALGORITHM` и `OSSL_DISPATCH`.
SDK не создаёт собственные большие структуры callbacks для digest, cipher
и других операций и не дублирует их сигнатуры.

`OPS_FUNCTION` оформляет одну запись dispatch. `OPS_DECLARE_ALGORITHM_DISPATCH`
объявляет цельный статический массив и добавляет завершающую запись. Отдельные
callbacks одного dispatch не собираются линкером из независимых фрагментов.

Объявление алгоритма обобщается до `OPS_DECLARE_ALGORITHM`, а получение списка —
до `ops_algorithms(operation_id)`. Для каждого поддержанного вида операции
предусматривается своя секция. Порядок записей внутри списка не является
контрактом. Новая операция не требует отдельного публичного getter или
дублирующего семейства объявлений.

Родные `OSSL_FUNC_*_fn` позволяют объявлять callbacks с сигнатурами OpenSSL.
Приведение указателя внутри `OPS_FUNCTION` не проверяет соответствие ID функции;
SDK не вводит такую проверку.

## Два источника записей

Источник выбирается отдельно для каждой операции. Автоматические записи одной
операции не смешиваются с внешним списком; разные операции могут использовать
разные способы доставки.

### Автоматические объявления

Пользователь объявляет dispatch и отдельные алгоритмы в удобных `.c` файлах.
`OPS_DECLARE_ALGORITHM` помещает непосредственную запись `OSSL_ALGORITHM`
в секцию соответствующей операции. Сборочный слой объединяет записи и
обеспечивает конечный список с терминатором.

Состав определяется сборкой. Списки, строки и dispatch действуют всё время
использования модулем и после публикации не изменяются. SDK не создаёт
динамический реестр и не передаёт вызывающему владение этим списком.

### Внешние записи

`OPS_DECLARE_EXTERN_RECORDS` подключает пользовательский источник готового
списка для выбранной операции. Здесь «внешний» означает предоставленный
пользователем, а не просто C-декларацию с ключевым словом `extern`.

Источник представлен функцией получения списка: это позволяет возвращать
как статический массив, так и таблицу, подготовленную при инициализации.
Окончательная сигнатура этого callback ещё не определена.

Пользователь отвечает за содержимое, терминаторы и время жизни внешних таблиц,
строк и функций. Он также организует освобождение динамически подготовленных
данных через согласованный механизм завершения. SDK доставляет результат без
валидации, копирования, объединения с автоматическими записями или
самостоятельного освобождения пользовательских данных.

Динамическое выделение таблицы не означает, что её можно произвольно менять
или освобождать после передачи OpenSSL. Указатели должны оставаться действительны
в соответствии с контрактом OpenSSL. Протокол замены опубликованных реализаций
не входит в эту политику.

## Жизненный цикл и состояние

Таблицы функций и состояние провайдера разделены. Статический dispatch
не запрещает открыть устройство, создать сессию или загрузить настройки при
инициализации. Контекст провайдера может хранить изменяемое состояние.

При исчезновении устройства опубликованная функция остаётся на своём месте,
а реализация операции сообщает об ошибке по контракту OpenSSL. SDK не снимает
объявление алгоритма автоматически. При отказе пользовательского init освобождение частично созданного
состояния выполняет сам init, согласно контракту lifecycle ниже.

Пользователь расширяет стандартный lifecycle обычными определениями
`ops_provider_user_init` и `ops_provider_user_cleanup`. Init получает готовый `provctx`
и адрес пользовательского `void *`; cleanup получает тот же `provctx` и указатель.
SDK хранит указатель, но не освобождает его самостоятельно. Доступ из алгоритма —
`ops_provider_get_user_data(provctx)`.

При отказе init пользователь сам освобождает частично созданное состояние;
cleanup в этом случае не вызывается. После успешного init cleanup вызывается
ровно один раз, пока core-обёртки ещё доступны. Подробности и пример:
[пользовательское состояние](provider-lifecycle.md).

## Размещение публичного интерфейса

Новые вложенные каталоги в дереве публичных заголовков создаются только по
явному указанию пользователя. Публичный `detail` удалён: в заголовке остались только атрибуты
пользовательского объявления, проверки layout и границы секций перенесены в `src/`.

`ops_algorithm.h` содержит пользовательские объявления алгоритмов. Общие
платформенные примитивы выносятся отдельно при реальной необходимости. Специфичные имена секций остаются рядом с механизмом
алгоритмов. Точные новые вспомогательные определения требуют предложения
и согласования.

Часть атрибутов должна быть доступна при раскрытии пользовательских макросов
в его translation unit. Границы секций, служебные начальные и конечные записи размещены в
`src/platform/linux.c` и `src/platform/windows.c`; общий контракт находится в
`src/platform/ops_platform.h`. Реализацию выбирает CMake. Проверка layout
остаётся в общем `src/ops_algorithm.c`. Пользователь не управляет ими напрямую.

## Текущая реализация и дальнейшие решения

| Решение | Состояние |
|---|---|
| `OPS_FUNCTION`, цельный `OPS_DECLARE_ALGORITHM_DISPATCH` | Реализованы |
| Секционные digest-записи и `ops_digest_algorithms()` | Реализованы; текущий специализированный интерфейс |
| Общие `OPS_DECLARE_ALGORITHM` и `ops_algorithms(operation_id)` | Согласовано направление; замена ещё не выполнена |
| `OPS_DECLARE_EXTERN_RECORDS` с функцией-источником | Согласован механизм; сигнатура и реализация предстоят |
| Стандартная точка входа SDK | Реализована для статического digest-реестра с отдельным core-контекстом на экземпляр |
| Пользовательские lifecycle-якоря и getter состояния | Реализованы |
| Удаление публичного `detail` и перенос служебных определений в реализацию | Выполнено |

До реализации общего интерфейса рабочие примеры используют существующие
имена из [ops_algorithm.h](../include/openssl_provider_sdk/ops_algorithm.h).
Новые имена выше не являются доступным API текущего checkout.

Отдельно предстоит определить сигнатуру внешнего источника,
поведение для неподдерживаемой операции и выбор источника при конфликтующей
конфигурации. Список поддержанных операций и способы подключения сборочных
настроек также нужно согласовать при реализации общего механизма.

## Платформенная граница

Общий код реестра и lifecycle вызывает контракт платформенного модуля:
получение плотного списка digest. Там же находятся реализации hooks по умолчанию,
которые заменяются определениями пользователя. Платформенный слой не владеет
пользовательским состоянием. Linux реализует ELF-секции и weak-определения,
Windows — COFF-секции и linker aliases. Экспорт точки входа задаётся через
`OPS_PROVIDER_EXPORT` из приватной конфигурации, сформированной CMake;
внутренняя видимость обеспечивается target-свойством `C_VISIBILITY_PRESET`.

Публичный макрос объявления записи по-прежнему содержит необходимые атрибуты
компилятора: он раскрывается в translation unit пользователя. Условия версий
OpenSSL сохраняют доступность новых core callbacks при старых заголовках.
